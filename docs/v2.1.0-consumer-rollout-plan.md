### Exact upgrade command

From the [v2.1.0 README Upgrade section](https://github.com/ExperienceQuality/xq-squad/blob/v2.1.0/README.md):

```bash
curl -LsSf https://github.com/ExperienceQuality/xq-squad/releases/download/v2.1.0/update.sh | sh -s -- --target . --version v2.1.0
```

`update.sh` requires `--target` and `--version vX.Y.Z`, downloads `squad-v2.1.0.tar.gz` and its `.sha256`, verifies the checksum, and refuses to start without Node.js 22+. It exits early if the installed version already matches. The Cursor hook `xq-squad-git-guard` will ask David to approve later `git commit`, `git push`, and `gh pr create`.

### Rollback (already documented)

From the [v2.1.0 README Rollback section](https://github.com/ExperienceQuality/xq-squad/blob/v2.1.0/README.md):

- Simplest path: `git revert` / `git checkout` of the upgrade commit.
- `update.sh --allow-downgrade` also moves to an older release.
- Manual fallback if there is no upgrade commit: delete the `.cursor/` files listed under `managed_files` in `.squad/install-state.json` (keep consumer-owned files), remove the `xq-squad-*` entries from `.cursor/hooks.json`, then reinstall the previous version into a clean checkout of `.squad/`.

Exact downgrade command after a v2.1.0 install:

```bash
curl -LsSf https://github.com/ExperienceQuality/xq-squad/releases/download/v2.0.0/update.sh | sh -s -- --target . --version v2.0.0 --allow-downgrade
```

### Doctor / validate

There is **no** consumer-facing `doctor` or `validate` command in v2.0.0 or v2.1.0. `scripts/validate.sh` is for the xq-squad source repository, not for an installed consumer. Post-upgrade checks are the install-state fields, the new skill file, conflict sidecars, and a Cursor smoke of `caveman` (section 5).

## 5. What to run and what to verify (every repo)

### Before

1. `node -v` — must be 22 or newer, or stop.
2. Start from an up-to-date default branch (`main`, or `master` for `xq-luthor`). Working tree clean, or at least no dirty overlap on `AGENTS.md`, `.squad/`, or `.cursor/`.
3. Branch `chore/xq-squad-v2.1.0` (or equivalent). Never commit the upgrade on the default branch directly.
4. Record the current `.squad/install-state.json` `version` / `release_tag` (expected `2.0.0` / `v2.0.0`).

### Upgrade

```bash
curl -LsSf https://github.com/ExperienceQuality/xq-squad/releases/download/v2.1.0/update.sh | sh -s -- --target . --version v2.1.0
```

In Cursor, the git-guard hook may ask David to approve the updater (`squad approve update` or the hook prompt). Ask before running if the hook requires it.

### After (success checks)

`update.sh` must exit 0, or every reported conflict must be resolved by hand and the sidecar deleted (section 9) before the repo is called done.

```bash
node -e 'const s=require("./.squad/install-state.json"); console.log(s.version, s.release_tag); process.exit(s.version==="2.1.0" && s.release_tag==="v2.1.0"?0:1)'
test -f .cursor/skills/caveman/SKILL.md
node -e 'const s=require("./.squad/install-state.json"); process.exit(s.managed_files[".cursor/skills/caveman/SKILL.md"]?0:1)'
# no leftover conflict sidecars
! git ls-files '*.squad-upstream' | grep -q .
```

There is no doctor/validate command to run.

**Cursor smoke (required by #28 for the new skill):** in a Cursor Agent session on that repo, trigger `/caveman` or "caveman mode", confirm the session uses the terse voice, then "stop caveman" or "normal mode". This is a smoke of the optional skill, not a new required contract.

**PR:** commit only squad upgrade changes (plus conflict resolutions). Suggested message: `chore: upgrade xq-squad to v2.1.0`. Open a PR to the default branch. In the body, reference [xq-squad#28](https://github.com/ExperienceQuality/xq-squad/issues/28), the updater output, any conflicts and how they were resolved, and the install-state / `caveman` checks.

### Evidence required to mark a repo upgraded

A repo is done only when **all** of the following are true on the **default branch**, not merely on a feature branch:

- The upgrade PR is **merged**.
- Default-branch `.squad/install-state.json` shows `"version": "2.1.0"` and `"release_tag": "v2.1.0"`.
- `.cursor/skills/caveman/SKILL.md` exists and is listed in `managed_files`.
- Conflicts were reported and resolved; no unresolved `*.squad-upstream` files remain (or any leftover is explicitly documented and accepted by David — the default is none).

Then update the tracker (§10) and, after a wave, only then start the next wave if David has not stopped the fleet.

## 6. Rollback rehearsal on the canary (before wave 2)

#28 requires a practiced per-consumer rollback on the canary using the README path, before later waves. Do this **on `xq-xcuitest-support` default branch history**, not only on an unmerged branch, so the rehearsal matches a real rollback after a shipped upgrade.

### Sequence

1. **Upgrade PR merged and verified** on `xq-xcuitest-support` `main` (section 5). Record the merge commit SHA (or the squash commit SHA, depending on how the PR is merged).
2. **Rollback PR** on a new branch from that `main`. Prefer the README's simplest path:

   ```bash
   git fetch origin
   git checkout -b chore/xq-squad-v2.1.0-rollback-rehearsal origin/main
   # If the upgrade landed as a single non-merge commit:
   git revert --no-edit <upgrade-commit-sha>
   # If the upgrade landed as a merge commit:
   git revert --no-edit -m 1 <upgrade-merge-sha>
   ```

   Alternative if revert is awkward (multiple commits, messy history):

   ```bash
   curl -LsSf https://github.com/ExperienceQuality/xq-squad/releases/download/v2.0.0/update.sh | sh -s -- --target . --version v2.0.0 --allow-downgrade
   ```

3. Verify rollback **after this PR is merged** to `main`:

   ```bash
   node -e 'const s=require("./.squad/install-state.json"); console.log(s.version, s.release_tag); process.exit(s.version==="2.0.0" && s.release_tag==="v2.0.0"?0:1)'
   test ! -f .cursor/skills/caveman/SKILL.md
   ```

   If `caveman` is still present after a `git revert`, stop and treat it as a rehearsal failure (the revert did not fully undo the upgrade).

4. **Re-upgrade PR** using the same v2.1.0 command as section 5. Merge it. Re-run the section 5 success checks on `main` (install-state 2.1.0 / v2.1.0, `caveman` present and registered, Cursor smoke).

5. Only then start wave 2.

If any step of this rehearsal fails, declare a fleet stop (§8). Do not start wave 2.

## 7. Success / stop checks (summary)

A **wave passes** when every repo in that wave meets the "evidence required" bar in section 5, and (for the canary) the rollback rehearsal in section 6 has also succeeded.

A **wave or canary fails** if any of the following happens and is not resolved in that same repo before calling it done:

- `update.sh` exits non-zero and the conflict cannot be resolved by hand, or consumer content was overwritten.
- After an attempted merge, default-branch install-state is not `2.1.0` / `v2.1.0`, or `caveman` is missing.
- Rollback rehearsal cannot return the canary to `2.0.0` / `v2.0.0`, or the re-upgrade fails.
- The Cursor smoke shows squad breakage beyond the optional skill voice (for example hooks or managed contracts clearly broken). A mere preference about caveman tone is not a failure.
- David judges the blast radius too high for any other observed reason.

## 8. Fleet-stop rule (process, not tooling)

#28: after a canary or wave failure, no further consumers are told to upgrade, and the stop is recorded. This is a written process, not new tooling.

- **Who decides:** David (Release Manager). No one else starts the next repo or wave after a suspected failure until David says so.
- **What happens:** stop giving local Cursor (or anyone) the next upgrade prompt. Do not open or merge further v2.1.0 consumer PRs. Already-open PRs in the failing wave are left open and not merged until David decides. Consumers not yet started stay on v2.0.0.
- **Already upgraded repos:** leave them on v2.1.0 unless David also wants a rollback. Per-consumer rollback is the README path in section 1 (revert or `update.sh --allow-downgrade`). There is no automated fleet rollback.
- **Record the stop:** comment on [xq-squad#28](https://github.com/ExperienceQuality/xq-squad/issues/28) with the date and time (Asia/Saigon), which repo failed, what failed (command output, conflict, install-state, rehearsal, smoke), which repos are already on v2.1.0, and that later waves are halted.
